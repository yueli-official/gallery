# 作品与角色

图库按照观众熟悉的主要所属作品或系列组织角色。角色只有一个直属父级，联动和客串不改变归属；游戏、动漫等媒体分类与这棵树独立。

```text
作品与角色（work）
├─ 碧蓝档案
│  └─ 普拉娜
├─ 独立角色
│  └─ 没有所属作品的原创角色
└─ 待归属角色
   └─ 出处暂不明确的角色
```

投稿和图片编辑可以只选作品，也可以只选具体角色；按作品浏览会包含角色后代的图片。多角色图片保留多个选择。作品根节点及角色共享最多 32 个赋值，保留原来两组各最多 16 项的数据容量。后台作品行提供“新增角色”，会预选所属作品；移动归属继续使用现有治理预览和执行流程。

实现复用 Foundation 的同 Facet 树、`parentId`、后代筛选与既有治理接口，没有新增跨维度关系或共享基础模块。投稿、浏览筛选、图片详情、后台目录、后台图片编辑及通用发布脚本同步使用该结构。

## 现有数据升级

后续迁移 `0023_work_character_tree.up.sql` 将 `character` 中的值迁入 `work`，保留值 ID、图片关联、投稿关联、角色封面和替代身份引用，删除空的旧角色维度。现有 PLN 数据中 `plana-blue-archive` 明确迁到 `blue-archive` 下；其他无父级角色进入“待归属角色”，不根据图片共现推断归属。原有角色子树保留其父子关系。

初始化只创建统一的 `work` 维度及两个角色分组，重复启动不会重新生成旧角色维度。PLN 导入入口也使用新的父子关系。

持久化的已保存筛选将 `character:值` 一次性迁成 `work:值`，同样处理接口允许的 UUID／短 ID 维度引用，保留冒号后原有值引用。旧作品和角色同时筛选时，原本是跨组 AND；只有各组至多单选的情况可自动保留为“同时出现”。包含多项 OR 的复杂组合会阻止迁移，需先明确调整该保存筛选。运行时不保留旧 `character:` URL 的兼容入口，外部旧链接需重新保存。

迁移遇到作品／角色标识重名，或旧角色维度自身仍有封面／被其他维度替代引用时，会整体失败并给出原因，需要先处理目录冲突。不会改标识、覆盖封面或忽略冲突继续。

发布时先备份数据库，配套更新 API、Web 和脚本。此迁移无法靠自动 down 安全拆回两组；回退需要恢复升级前数据库备份及对应旧制品。脚本 1.2.0 遇到旧目录会停止，避免将角色误建成作品根节点。
